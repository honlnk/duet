## 一、项目愿景

将 Duet 从「辩论工具」进化为**纯 AI 对话酒馆**——让多个 AI 角色像真实人物一样自然对话，角色之间有深度感知、有情感关系、有信息差。

核心差异化：利用 Duet **独立记忆架构**的结构性优势，实现 SillyTavern 群聊做不到的**非对称多角色感知**。

---

## 二、当前架构的核心缺陷

### 缺陷 1：角色之间互不感知（致命）

A 发言时只知道 B 的名字，不知道 B 的性别、性格、身份。

`AgentMemory.others: AgentRef[]` 已持有对方完整 persona，但 prompt 拼装时只取了 `o.name`，persona 完全丢弃。

### 缺陷 2：角色设定过于简陋

只有 `name + persona(自由文本) + color`，没有结构化的性格/背景/外观/开场白/对话示例。

### 缺陷 3：缺少全局提示词层

没有独立的场景设定 / 世界观 / 导演指令。topic 兼做引子和设定，职责不清。

---

## 三、核心创新：非对称关系图

### 3.1 设计灵感

SillyTavern 群聊没有解决多角色互相感知问题：
- Swap 模式：角色互不可见（和当前 Duet 一样）
- Join 模式：全量融合角色卡，容易人格混淆

**Duet 的结构性优势**：每个 agent 有独立的 `AgentMemory`，`buildApiMessages()` 是逐个 agent 调用的。这意味着 A 和 B 可以看到**完全不同的 system prompt**——非对称感知天然成立。

> 酒馆做不到，是因为它们多角色共享同一套上下文；Duet 各自维护各自的，天然适合非对称感知。

### 3.2 有向关系图

维护一个**有向、非对称**的关系矩阵：

```
Key 格式: "{fromId}->{toId}"
值: from 视角下对 to 的关系描述（第一人称、主观认知）
```

对于 N 个角色，有 N×(N-1) 条有向关系：
- 2 人 = 2 条（A→B、B→A）
- 3 人 = 6 条
- 10 人 = 90 条

**核心特性：同一段关系，两个角色的认知可以完全不同。**

### 3.3 示例：小张与小美

角色设定：
- **小张**：阳光帅气，打篮球，说话喜欢调侃人
- **小美**：漂亮温柔，学习很好，笑起来非常可爱

客观关系：两人是同学/同桌，小美暗恋小张，小张隐约感觉到但不想戳破。

**小张发言时的 system prompt（A→B 视角）：**

```
─── 主角设定 ───
我的名字是小张，性别男。我喜欢打篮球，长得帅气，性格阳光开朗，
说话的时候喜欢调侃人……

─── 在场角色 ───
小美：女，你的同学。学习很好，长得漂亮，温柔善良，笑起来非常可爱……

─── 我与小美的关系 ───
小美是我的同桌，学习很好的女生。她好像什么事都愿意由着我，
对我有一点什么不一样的情愫在？但我不想戳破那层窗户纸。
```

**小美发言时的 system prompt（B→A 视角）：**

```
─── 主角设定 ───
我的名字是小美，性别女。我学习很好，长得漂亮，温柔善良，
笑起来非常的可爱……

─── 在场角色 ───
小张：男，你的同学。喜欢打篮球，长得帅气，性格阳光开朗，
说话喜欢调侃人……

─── 我与小张的关系 ───
小张是我的同桌，同时也是我的Crush。这家伙学习笨笨的就爱玩那个篮球，
每次都背着我偷偷抄我作业，但都能被我发现，我好像也没有那么生气。
```

**信息差对比：**

| 维度 | 小张视角 (A→B) | 小美视角 (B→A) |
|---|---|---|
| 关系定位 | 「同桌」 | 「我的Crush」 |
| 确定程度 | 模糊猜测（「好像」「似乎」） | 明确认知 |
| 情感投入 | 回避（「不想戳破」） | 主动（暗恋） |
| 抄作业 | 「经常偷偷抄」 | 「每次都被我发现」 |

这种信息差是真实社交的动力引擎——**误解、暧昧、错位**都来自于此。

## 四、功能需求

### 4.1 结构化角色卡（需求-高）

把单一 `persona` 字段升级为结构化角色信息。

**最小字段集：**

| 字段 | 用途 | 必填 |
|---|---|---|
| `name` | 角色名 | ✅ |
| `description` | 综合身份描述（背景/外貌/核心设定） | ✅ |
| `personality` | 性格关键词摘要 | 可选 |
| `color` | 颜色标识 | 可选 |

**向后兼容**：旧 `persona` 字段保留，prompt 构造时 `description || persona` 回退。

**扩展字段（后续可加）：**

| 字段 | 用途 | 阶段 |
|---|---|---|
| `mesExample` | 对话示例（教说话方式） | 三期 |
| `scenario` | 角色个人场景 | 二期 |

> **不做自定义开场白（firstMes）**：酒馆需要 firstMes 是因为 AI 先开口、用户不知道聊什么；Duet 的开场由「话题」驱动，不需要这个功能。

### 4.2 非对称关系图（需求-高，核心创新）

#### 数据模型

```ts
interface Session {
  // ... 现有字段 ...
  relationships?: Record<string, string>
  // Key: "{fromId}->{toId}"，值: from 视角对 to 的关系描述
}
```

#### 行为需求

1. **注入时机**：每次 agent 发言时，在 system prompt 中注入该 agent 对所有其他在场角色的关系描述
2. **第一人称**：关系描述以当前 agent 的第一人称撰写（「我的同桌」「我的Crush」）
3. **主观性**：允许信息差、误解、暧昧——不同角色对同一段关系的认知可以完全不同
4. **抗压缩**：关系描述在 system prompt 中（永久层），每次动态重建，不会被摘要压缩丢失
5. **可选性**：没有配置关系的角色之间，回退到「仅名字 + 精简描述」

#### prompt 注入位置

```
system 1: 全局设定（场景/世界观/导演指令）     ← 4.3
system 2: 主角设定（自己的角色卡）              ← 4.1
system 3: 在场角色（他人的精简描述）            ← 4.4
system 4: 我与其他人的关系（非对称，第一人称）  ← 本节核心
system 5: 对话规则
system 6: 摘要（若有）
─── 滚动历史 ───
```

### 4.3 全局提示词与世界观模板（需求-中）

#### 4.3.1 会话级字段

在会话级新增独立的场景/世界观/导演指令层：

| 字段 | 用途 | 示例 |
|---|---|---|
| `scenario` | 场景设定 / 世界观 | 「深夜的咖啡馆，窗外下着雨」 |
| `globalPrompt` | 导演指令 / 全局规则 | 「对话基调为悬疑，角色之间暗藏秘密」 |

与 topic 的职责分离：
- `topic` = 对话主题/引子（「讨论 XX」）
- `scenario` = 场景/世界观（「赛博朋克听证会」）
- `globalPrompt` = 导演指令（「逐步升级为争论」）

#### 4.3.2 世界观模板（可复用）

`scenario + globalPrompt` 如果每次建对话都要重填，体验很差。用户想反复用同一个世界观（如「赛博朋克 2077」「校园日常」）时，应该能像角色模板、话题模板一样保存复用。

**三类模板正交组合**——正好对应一场戏的三个要素：

| 模板类型 | 隐喻 | 复用内容 | 现状 |
|---|---|---|---|
| 智能体模板 | **演员** | 角色卡（name + description + personality） | ✅ 已有 |
| 话题模板 | **剧本主题** | 对话引子（topic） | ✅ 已有 |
| **世界观模板** | **舞台** | **场景 + 导演指令（scenario + globalPrompt）** | **❌ 待新增** |

三者正交：一个世界观可以配不同的角色组合，一个角色也可以放进不同的世界观，话题更是独立。三者自由组合 = 一场完整的戏。

**数据模型**（与现有模板对称，存 localStorage）：

```ts
interface ScenarioTemplate {
  id: string
  name: string              // 模板名（如「校园日常」「赛博朋克」）
  scenario: string          // 场景设定
  globalPrompt?: string     // 导演指令（可选）
  createdAt: number
}
```

**使用方式**：新建对话时，用户可从世界观模板列表中选用一个，一键填入 `scenario + globalPrompt`（交互方式与现有话题模板一致）。也可不选——scenario / globalPrompt 均为可选字段。

### 4.4 他人精简描述注入（需求-高）

发言者拿自己的**完整角色卡**，其他在场角色拿**精简描述**。

精简策略待定（见决策点），但原则是：让对方知道「这个人是谁」的关键信息，但不注入完整角色卡（避免人格混淆）。

### 4.5 导演 Agent（需求-中，可选增强）

导演 Agent 有两个职责：**预处理**（对话前）和**运行时干预**（对话中）。

#### 4.5.1 预处理：自动生成关系描述（对话前）

用户输入角色卡 + 简单关系标签（"同学""暗恋""竞争对手"），导演 Agent 调用一次 LLM，自动生成非对称关系描述供用户确认。

```
用户输入：角色卡 + 关系标签
     ↓ 导演 Agent（一次 LLM 调用）
自动生成：A→B、B→A 两条非对称关系描述
     ↓ 用户确认/编辑
写入 session.relationships
```

**定位**：可选。2 人场景可直接手写关系描述，跳过此步。

#### 4.5.2 运行时干预：临时导演指令（对话中，核心新需求）

对话进行过程中，用户可以通过导演 Agent 注入一段**高权重临时指令**，改变聊天方向。

**典型场景**：
- 对话陷入循环 / 偏离主题 → 注入「请把话题转回 XX」
- 想推动剧情发展 → 注入「小张，试着主动问小美一个问题」
- 想制造冲突 → 注入「下一轮开始，两人因为某个误会产生分歧」

**核心机制：TTL（保质期）**

临时指令不是永久注入的——它有**轮数保质期**：

```
用户注入：「请让小张主动提起周末计划」，TTL = 3 轮

第 1 轮：指令注入 system prompt（高权重，靠后放置增强影响力）
第 2 轮：指令继续注入
第 3 轮：指令继续注入
第 4 轮：指令自动移除，释放 prompt 空间
```

**为什么需要 TTL**：
- 一般几轮对话后，话题风向已经转向期望结果，不再需要强制约束
- 永久占用 prompt 空间会浪费 token，且堆积过多指令会互相冲突
- TTL 到期自动清理，释放空间给下一次控场

**数据模型**：

```ts
interface DirectorDirective {
  id: string
  content: string         // 指令内容
  ttlRounds: number       // 保质期（剩余轮数）
  injectedAt: number      // 注入时的 round
}
```

注入时 TTL 倒计时，每完成一轮 TTL-1，TTL 归零自动移除。用户也可手动提前移除。

#### 4.5.3 prompt 注入位置

```
system 1: 全局设定（场景/世界观/导演指令）
system 2: 主角设定（自己的角色卡）
system 3: 在场角色（他人的精简描述）
system 4: 我与其他人的关系（非对称）
system 5: 对话规则
system 6: 摘要（若有）
system 7: 🎬 临时导演指令（若有，高权重）   ← 新增，靠近滚动历史增强影响力
─── 滚动历史 ───
```

临时指令放在 system 最末尾（紧邻滚动历史之前），因为越靠后的指令对模型输出的影响权重越大（recency bias）。这和 SillyTavern 的 Depth 0 注入同理。

### 4.6 关系图管理页（需求-高）

#### 4.6.1 设计定位

关系编辑**不在新建对话流程里完成**，而是做成一个**独立的可视化关系图管理页**。

用户在这里：
- 看到所有角色以节点形式呈现
- 在节点之间画线建立关系
- 点击连线打开弹窗，编辑两个视角的关系描述

#### 4.6.2 交互设计

```
┌─────────────────────────────────────────┐
│              关系图管理页                 │
│                                         │
│    ┌────────┐              ┌────────┐   │
│    │  小张   │────── 连线 ───│  小美   │   │
│    │ 打篮球  │              │ 学习好  │   │
│    └────────┘              └────────┘   │
│                                         │
│  · 从节点边缘拖拽 → 连线到另一个节点      │
│  · 点击连线 → 打开编辑弹窗               │
│  · 弹窗内有两个文本框（A视角 / B视角）    │
│  · 节点可拖动定位                        │
└─────────────────────────────────────────┘
```

**操作流程**：
1. 页面展示所有角色节点（从角色模板 / 当前会话角色加载）
2. 用户从节点边缘拖拽一条连线到另一个节点 → 创建双向关系
3. 点击连线 → 打开弹窗：
   - 文本框 1：A 视角下对 B 的关系描述（第一人称）
   - 文本框 2：B 视角下对 A 的关系描述（第一人称）
4. 保存 → 写入 `session.relationships["A->B"]` 和 `["B->A"]`

#### 4.6.3 技术选型

**渲染库：Vue Flow**（`@vue-flow/core`）

| 考量 | 结论 |
|---|---|
| Vue 3 + TS 原生 | ✅ 完全用 TypeScript 编写，原生 Vue 3 |
| 自定义节点 | ✅ 显示角色名 + 描述摘要 |
| 拖拽连线 | ✅ 从 handle 拖拽创建连接 |
| 边点击事件 | ✅ `@edge-click` 打开弹窗 |
| 节点拖动定位 | ✅ XY 坐标持久化 |
| 维护活跃度 | ✅ 6.8k star，2026-07 仍在更新 |
| 双向关系处理 | 边数据有方向（source/target），UI 隐藏箭头即可表示双向 |

**关于 Obsidian JSON Canvas**：它是纯数据格式规范（`.canvas` 文件），不是渲染库。可选地，未来在 Vue Flow 之上套一层 JSON Canvas schema 作为导出格式，获得与 Obsidian 互通的能力。V1 不需要。

#### 4.6.4 数据持久化

关系图管理页产出的关系数据存入 `session.relationships`：

```ts
// 2 人场景，连接一条线 = 两条关系描述
relationships: {
  "A->B": "小美是我的同桌，学习很好的女生……（小张视角）",
  "B->A": "小张是我的Crush，这家伙学习笨笨的……（小美视角）"
}
```

节点位置（XY 坐标）可选持久化到 session，让用户下次打开管理页时布局不变。

## 附录：为什么 Duet 能做到酒馆做不到的事

```
酒馆（共享上下文）：
  所有角色共用一份 message history
  → 每次只能注入一套 system prompt
  → A 和 B 看到的关系描述必须相同
  → 非对称感知不可能实现

Duet（独立记忆）：
  每个 agent 有独立的 AgentMemory
  → buildApiMessages() 逐个 agent 调用
  → A 和 B 可以看到完全不同的 system prompt
  → 非对称感知天然成立
```
